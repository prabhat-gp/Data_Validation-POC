PROJECT SUMMARY (As of Jul 28, 2026)

Project:
SMTC Data Validation Framework

Goal:
Build a configurable data validation platform for Salesforce data (currently Honeywell Aerospace Account data as placeholder, future target = Onity SFDC Account data).

Current Direction:
- Dashboard-first approach.
- Define dashboard -> define metrics -> define violations -> define validation framework.
- Web application replaces Power BI.
- Focus on Data Validation + Violation Reporting only in V1.
- Remediation lifecycle (Open / Fixed / Won't Fix / Aging) postponed to later phases.

----------------------------------------------------------------------
VALIDATION EXECUTION STRATEGY
----------------------------------------------------------------------

Two rule categories:

1. Single Row Rules (formerly Query-Centric)

Examples:
- Not Null
- Allowed Values
- Regex
- Format
- Range
- Cross-field checks

These evaluate only one record at a time.

Examples:

Name IS NOT NULL

BillingCountry IN (...)

Website matches URL pattern

These run directly against staging data.

Expected:
~80-90% of rules

------------------------------------------------

2. Whole Set Rules (formerly Record-Centric)

Examples:
- Duplicate checks
- Uniqueness
- Parent-child cardinality
- Certain reference integrity checks

Need comparison across records.

Expected:
~10-20% of rules

For V1:
No separate key-index table yet.

Can revisit later if data volume requires it.

----------------------------------------------------------------------
FINAL V1 DATABASE SCHEMA
----------------------------------------------------------------------

1. DQ_OBJECT

Purpose:
Stores validated object information.

Columns:

object_id (PK)
object_name
source_system
record_key_column

Example:

object_name = Account
source_system = SFDC
record_key_column = Id

------------------------------------------------

2. DQ_ELEMENT

Purpose:
Stores CDEs being validated.

Columns:

element_id (PK)
object_id (FK)
element_name
source_column_name
data_type

Contains only the selected 16 matched CDEs.

------------------------------------------------

3. DQ_RULE

Purpose:
Stores validation rules.

Columns:

rule_id (PK)
object_id (FK)
element_id (FK)
rule_name
rule_type
dimension
severity
rule_config_json
condition_expr
status
created_by
created_at

Status values:

draft
submitted
approved

Only approved rules execute.

------------------------------------------------

4. DQ_RUN

Purpose:
Stores validation execution history.

Columns:

run_id (PK)
object_id (FK)
run_type
status
started_at
finished_at
records_scanned
source_file_name
error_message

Kept:
- started_at
- finished_at

Reason:
Need run auditing and execution tracking.

------------------------------------------------

5. DQ_VIOLATION

Purpose:
Stores failed records.

One row per:
record + rule + run

Columns:

violation_id (PK)
run_id (FK)
object_id (FK)
element_id (FK)
rule_id (FK)
record_key
current_value
violation_reason
severity
dimension

Removed:
- fix_status
- assigned_to
- open/closed
- times_seen
- lifecycle tracking

------------------------------------------------

6. DQ_METRIC

Purpose:
Dashboard consumption table.

Columns:

metric_id (PK)
run_id (FK)
object_id (FK)
element_id (FK)
rule_id (FK)
dimension
severity
records_checked
records_failed
score_pct

Used for:

- KPI cards
- Heatmap
- Dimension scores
- Drilldowns

------------------------------------------------

7. STG_SOURCE_RECORD (Runtime Only)

Purpose:
Temporary validation dataset.

Columns:

run_id
record_key
16 selected CDE columns
loaded_at

Data removed after validation run.

Not permanent storage.

RULE TYPES SUPPORTED IN V1
----------------------------------------------------------------------

Required
Allowed Values
Format Pattern
Max Length
Unique
Conditional Required

Examples:

Name IS NULL

Allowed Values:
BillingCountry NOT IN (...)

Format Pattern:
Website invalid URL

Unique:
Duplicate Account Number

Conditional Required:
If Account_Status = Active
then Phone is mandatory

----------------------------------------------------------------------
RULE AUTOMATION STRATEGY
----------------------------------------------------------------------

Do NOT use OpenAI as core architecture.

Preferred approach:

Metadata + Profiling + Templates

Example:

Field contains "Country"
→ Suggest Allowed Values

Field contains "Phone"
→ Suggest Phone Format

Field contains "Website"
→ Suggest URL Format

Field has 98% population
→ Suggest Required

Field has small cardinality
→ Suggest Allowed Values

Generated rules enter:

DQ_RULE.status = 'draft' or 'submitted'

Human reviews.

Then:

status = approved

Only approved rules execute.

----------------------------------------------------------------------
RULE EXECUTION MODEL
----------------------------------------------------------------------

Validation Engine loads:

SELECT *
FROM DQ_RULE
WHERE status = 'approved'

For each rule:

1. Compile metadata to SQL.
2. Run against staging.
3. Capture violations.
4. Generate metrics.

No developer involvement.

----------------------------------------------------------------------

----------------------------------------------------------------------

1. Only 16 matched CDEs in scope.
2. No remediation lifecycle.
3. No watermark columns.
4. No Power BI.
5. Web application only.
6. Rules are metadata, not code.
7. Non-technical users can create rules.
8. Approved rules automatically run in future validations.
9. Dashboard reads DQ_METRIC and DQ_VIOLATION directly.
10. Focus strictly on validation and violation reporting.
