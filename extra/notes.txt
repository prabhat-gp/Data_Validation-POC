################################################################################
PART 1 — RULE TYPES
################################################################################

There are 8 rule types. A rule is never code — it is a ROW in the val_rules
table. The engine reads that row and compiles it into SQL at run time. That is
why a business user can add a rule through the web UI with no developer and no
deployment.

Two things the user picks are turned into everything else by the backend:
  - rule_type        -> decides the dimension, and which SQL template is used
  - rule_definition  -> the values the user typed (allowed list, regex, etc.)
Everything else (dimension, execution_type, rule_name, rule_id, source_system,
primary_key_field) is GENERATED server-side.

OPTIONAL SCOPE FILTER (all 8 types, including Required and Unique):
  Any rule may carry a "filter" that limits WHICH RECORDS it checks:
      {"filter": {"conditions": [{"field":"Type","operator":"=",
                                  "value":"Owner/Operator"}], "logic":"AND"}}
  Required + filter  -> WHERE (Type='Owner/Operator')
                          AND (BillingCity IS NULL OR TRIM(BillingCity)='')
  Unique   + filter  -> the filter is applied to BOTH passes. Applying it only
                        to pass 1 would find duplicates inside the filtered
                        subset, then report every row sharing that value --
                        including rows outside the filter. Silent false
                        positives.
  Empty/absent filter == check the whole table (previous behaviour).

--------------------------------------------------------------------------------
HOW RULES EXECUTE — "query-centric" vs "record-centric"
--------------------------------------------------------------------------------

7 of the 8 types are QUERY-CENTRIC (single-row): to judge one record you only
need that record. They compile to one SELECT ... WHERE <failing condition>.

1 of the 8 is RECORD-CENTRIC (whole-set): Unique. You cannot tell whether a
value is duplicated by looking at one row — you must compare across all rows.
Per the agreed direction, it is STILL just plain SQL (GROUP BY / HAVING), run
through the same execution path. There is no separate rules-engine.

IMPORTANT: this classification is DERIVED from rule_type (see RULE_TYPE_META
in rule_compiler.py) and stored on val_rules.execution_type for reporting.
It is never accepted from the client -- otherwise a 'required' rule could be
marked RECORD and sent down the wrong engine path.

--------------------------------------------------------------------------------
1. REQUIRED                                   (dimension: Completeness)
--------------------------------------------------------------------------------
What it does : The field must not be empty. Blank or NULL = violation.
Example      : Every Account must have a Name.
User fills   : Entity=Account, Field=Name, Rule Type=Required, Severity=Critical
               (optionally a scope filter -- see above)
Compiles to  : WHERE Name IS NULL OR TRIM(Name) = ''
Execution    : Query-centric (single row)

--------------------------------------------------------------------------------
2. ALLOWED VALUES                             (dimension: Validity)
--------------------------------------------------------------------------------
What it does : Value must be one of a fixed list. Anything else = violation.
Example      : BillingCountry may only be US, IN or GB.
User fills   : Field=BillingCountry, Rule Type=Allowed Values,
               Allowed Values = "US, IN, GB", Severity=Warning
Config JSON  : {"values": ["US","IN","GB"]}
Compiles to  : WHERE BillingCountry IS NOT NULL AND TRIM(BillingCountry) <> ''
                 AND BillingCountry NOT IN ('US','IN','GB')
Execution    : Query-centric (single row)
NOTE         : Blank values are ignored here on purpose — that is the job of a
               separate Required rule. One rule, one responsibility.
WATCH OUT    : the list must match the data EXACTLY. Real Account data holds
               "USA" and "Italy" (full names), not ISO codes — configuring
               "US, IN, GB" against it failed 100% of rows in testing.

--------------------------------------------------------------------------------
3. FORMAT PATTERN                             (dimension: Format)
--------------------------------------------------------------------------------
What it does : Value must match a regular expression.
Example      : Website must start with http:// or https://
User fills   : Field=Website, Rule Type=Format Pattern,
               Pattern = "^https?://", Severity=Warning
Config JSON  : {"pattern": "^https?://"}
Compiles to  : WHERE Website IS NOT NULL AND TRIM(Website) <> ''
                 AND NOT REGEXP('^https?://', Website)
Execution    : Query-centric (single row)
NOTE         : REGEXP is registered as a custom function for SQLite. On Oracle
               or Postgres this becomes REGEXP_LIKE / the ~ operator — the one
               genuinely database-specific piece in the engine.

--------------------------------------------------------------------------------
4. MAX LENGTH                                 (dimension: Format)
--------------------------------------------------------------------------------
What it does : Value must not exceed a character limit.
Example      : BillingPostalCode must be 20 characters or fewer.
User fills   : Field=BillingPostalCode, Rule Type=Max Length,
               Max Length = 20, Severity=Warning
Config JSON  : {"max_length": 20}
Compiles to  : WHERE LENGTH(BillingPostalCode) > 20
Execution    : Query-centric (single row)

--------------------------------------------------------------------------------
5. UNIQUE                                     (dimension: Uniqueness)
--------------------------------------------------------------------------------
What it does : No two records may share the same value.
Example      : Two Accounts must not have the same Name.
User fills   : Field=Name, Rule Type=Unique, Severity=Warning
               (optionally a scope filter -- see above)
Compiles to  : SELECT Name FROM stg_account
                 WHERE run_id = ? AND Name IS NOT NULL AND TRIM(Name) <> ''
                 GROUP BY Name HAVING COUNT(*) > 1
               ...then a second pass pulls every record_key sharing those values,
               so BOTH sides of a duplicate pair are reported.
Execution    : RECORD-CENTRIC (whole set) — the only one. Still plain SQL.

--------------------------------------------------------------------------------
6. CONDITIONAL REQUIRED                       (dimension: Consistency)
--------------------------------------------------------------------------------
What it does : A field is mandatory ONLY when another field has a given value.
Example      : If Type = 'Owner/Operator', then Phone must be filled in.
User fills   : Field=Phone (the field being required),
               Rule Type=Conditional Required,
               "If Field: If Value" = "Type:Owner/Operator"
Config JSON  : {"if_field": "Type", "if_value": "Owner/Operator"}
Compiles to  : WHERE Type = 'Owner/Operator'
                 AND (Phone IS NULL OR TRIM(Phone) = '')
Execution    : Query-centric — both fields are on the SAME row.
NOTE         : This handles ONE condition. For several chained conditions use
               Multi-Condition (#8).

--------------------------------------------------------------------------------
7. REFERENTIAL INTEGRITY                      (dimension: Ref Integrity)
--------------------------------------------------------------------------------
What it does : The value must already exist in ANOTHER object's field.
               The classic foreign-key check.
Example      : Every Account.BillingCountry must be a country that already
               appears in Contact.BillingCountry.
User fills   : Field=BillingCountry (the column on THIS object),
               Rule Type=Referential Integrity,
               Reference Object=Contact, Reference Field=BillingCountry
Config JSON  : {"ref_entity_name": "Contact", "ref_field_name": "MailingCountry"}
Compiles to  : WHERE BillingCountry IS NOT NULL AND TRIM(BillingCountry) <> ''
                 AND BillingCountry NOT IN (
                       SELECT value FROM val_reference_values
                       WHERE entity_name = ? AND field_name = ?)
Execution    : Query-centric (LEFT JOIN / NOT IN pattern) — one SQL query.

  ** WHY A SEPARATE val_reference_values TABLE? **
  Staging is wiped after every run (it is runtime-only, by design).
  So when Account validates, Contact's staged rows may already be gone — a
  direct cross-object JOIN is impossible. Instead, at the end of each run the
  engine captures the DISTINCT values of any element that some approved
  ref_integrity rule points at, into val_reference_values. Small, bounded,
  indexed — not a copy of the source data.

  ** BOOTSTRAPPING BEHAVIOUR (important, not a bug) **
  A ref_integrity rule can only see values captured by the REFERENCED object's
  most recent completed run. If that object has never been validated, the
  reference set is empty and the rule fails every row.
  Verified in testing:
      Run 1 -> 101 of 101 failed  (reference set empty)
      Run 2 -> 0 of 101 failed    (reference set now populated by Run 1)
  So: always run the referenced object at least once first.

--------------------------------------------------------------------------------
8. MULTI-CONDITION (ADVANCED)                 (dimension: Consistency)
--------------------------------------------------------------------------------
What it does : Chain SEVERAL conditions on the same record with AND/OR, then
               either require a field or simply flag the record.
Example      : If Type = 'Owner/Operator' AND BillingCountry = 'USA',
               then BillingCity must be filled in.
User fills   : Rule Type=Multi-Condition. The single "Field" dropdown is
               REPLACED by a condition builder:
                   Condition rows : [Field] [Operator] [Value]   (+ Add)
                   Match          : ALL (AND) / ANY (OR)
                   Then           : Require a field  ->  pick the field
                                    OR  Just flag the record
Operators    : equals, not equals, is one of (comma list), is empty, is not empty
Config JSON  : {"conditions":[{"field":"Type","operator":"=","value":"Owner/Operator"},
                              {"field":"BillingCountry","operator":"=","value":"USA"}],
                "logic":"AND",
                "then":{"type":"require","field":"BillingCity"}}
Compiles to  : WHERE (Type = 'Owner/Operator' AND BillingCountry = 'USA')
                 AND (BillingCity IS NULL OR TRIM(BillingCity) = '')
Execution    : Query-centric — every field referenced is on the SAME row, so it
               is one multi-clause WHERE.

  ** HONEST LIMITATION **
  This is NOT a Drools / SAP BRF+ style rules engine. It does not load the
  record into memory as a "fact", and one rule cannot depend on another rule's
  outcome. If that is ever needed it is a separate, heavier piece of work.

  ** "then: flag" vs "then: require" **
  require -> violation when the conditions match AND the target field is empty
  flag    -> violation whenever the conditions match, full stop
             (use it to report on a segment, e.g. "list every Temporary account
             in the USA")

  ** WHICH field_name gets stored? **
  val_rules.field_name is NOT NULL, but a multi-condition rule has no single
  field. The UI stores the field the rule is most "about": the require-target,
  or the first condition's field for a flag-only rule.

  ** VERIFIED CORRECT **
  Tested on the real 101-row sample:
    rule  : IF Type='Owner/Operator' THEN require BillingCity
    manual count of matching rows in the CSV : 37
    engine result                            : 37 failed, score 63.37%
    -> exact match.


################################################################################
PART 2 — DATABASE SCHEMA (val_* single-rules-table design)
################################################################################

CONFIG is now a SINGLE table: val_rules. There is no separate object or
element catalog -- a rule row carries entity_name / field_name /
primary_key_field directly, so it is self-describing.

The entity catalog lives in the ENTITIES constant in app/models.py (known up
front, not discovered at upload time). That is what feeds the Rules page
dropdowns -- you cannot derive a field list from rules that don't exist yet.

--------------------------------------------------------------------------------
LOOKUP TABLES (tiny, constrain values + give the UI a description)
--------------------------------------------------------------------------------
val_rule_types    code, description, dimension, execution_type   (8 rows)
val_severities    code, description                              (Critical/Warning)
val_statuses      code, description                              (draft/submitted/
                                                                  approved/rejected)

--------------------------------------------------------------------------------
val_rules  -- CONFIG. One row = one rule.
--------------------------------------------------------------------------------
rule_id            PK, Varchar(50). Readable: ACCOUNT_NAME_REQUIRED_001.
                   Chosen over a UUID because these get discussed in meetings
                   and read in logs.
rule_name          Display label.
source_system      e.g. "SFDC". Stamped from the entity catalog.
rule_type          FK -> val_rule_types. Picks which SQL template compiles.
entity_name        Which object. (Replaces the old dq_object FK.)
field_name         Which column. (Replaces the old dq_element FK.)
primary_key_field  Which column identifies a record ("Id"). This is what makes
                   a violation actionable rather than "row 4,782 failed".
execution_type     QUERY | RECORD. DERIVED from rule_type on save, never
                   accepted from the client -- otherwise a 'required' rule
                   could be marked RECORD and take the wrong engine path.
rule_definition    ** SOURCE OF TRUTH ** the JSON the user configured.
                   NOTE: the compiled SQL is deliberately NOT stored. It is
                   regenerated from this on every run, so the two can never
                   drift out of sync.
error_message      Optional custom text stamped onto each violation.
severity           FK -> val_severities. Drives dashboard weighting.
status             FK -> val_statuses. THE APPROVAL GATE: only 'approved'
                   rules are ever loaded by the engine. A draft rule exists
                   but is completely inert.
active             Retire a rule without deleting its history.
created_by         Who authored it.
created_date       When.
updated_by         Last editor -- changes on ANY edit.
updated_date       "
approved_by        ** WHO approved it. ** Kept separate from updated_by
approved_date      precisely because updated_* changes on any edit and so
                   cannot serve as an approval record.
                   Enforced: approved_by != created_by (separation of duties).

--------------------------------------------------------------------------------
val_batches  -- what a user calls "a run": one trigger, 1..N entities
--------------------------------------------------------------------------------
batch_id           PK autoincrement. DB-generated, so two concurrent triggers
                   can't collide on the same id.
batch_name         "Run #3" / "Nightly 02 Aug".
run_type           file_upload | db_fetch.
triggered_by       Who clicked it.
started_at         When.

NOTE: batch STATUS is not stored -- it is derived from the child runs
(any running -> running; any failed -> completed_with_errors; else
completed). Deriving it means a crash can't leave a stored status
permanently wrong.

--------------------------------------------------------------------------------
val_runs  -- ONE ENTITY's execution inside a batch
--------------------------------------------------------------------------------
run_id             PK.
batch_id           FK -> val_batches.
entity_name        Which entity this run validated.
run_type           file_upload | db_fetch.
status             pending|running|completed|failed. The dashboard reads ONLY
                   'completed', so a broken run is invisible not misleading.
started_at         Run auditing + ordering.
finished_at        "
records_scanned    Feeds the "Records Scanned" KPI; denominator for scores.
rules_executed     How many approved rules actually ran.
source_file_name   Traceability for uploads.
error_message      If failed, what went wrong.

WHY ONE RUN PER ENTITY: a batch of 4 entities is 4 runs. If Contact fails on
a missing column, Account still completes and keeps its results. The dashboard
asks for "latest completed run per entity", so entities validated in different
batches still show correctly side by side.

--------------------------------------------------------------------------------
val_metrics  -- the dashboard's fact table. One row per rule per run.
--------------------------------------------------------------------------------
metric_id          PK.
run_id             FK -> val_runs.
rule_id            The rule -- NOT an FK, deliberately: results must outlive
                   rule edits and deletions.
entity_name        Denormalized at write time.
field_name         Denormalized at write time.
dimension          Denormalized -- so the dashboard never joins to val_rules,
severity           and so history stays correct if a rule's severity changes.
records_checked    Denominator.
records_failed     Feeds the Critical KPI.
score_pct          Computed ONCE at run close. This is why the dashboard is
                   instant: it reads a few hundred pre-computed rows, never a
                   live scan of millions of violations.

--------------------------------------------------------------------------------
val_violations  -- the fix team's worklist. One row per failing record per rule.
--------------------------------------------------------------------------------
violation_id       PK.
run_id             FK -> val_runs.
rule_id            Which rule flagged it (not an FK, same reasoning).
entity_name        Denormalized.
field_name         Denormalized.
record_key         THE SOURCE Id -- what makes a violation actionable.
current_value      The actual bad value, so triage needs no round trip.
violation_reason   Human-readable message.
severity           Denormalized at write time.
dimension          "
INDEXES            (run_id, entity_name), (run_id, rule_id), (run_id, severity)

--------------------------------------------------------------------------------
val_reference_values  -- supports Referential Integrity
--------------------------------------------------------------------------------
id                 PK.
entity_name        Where these values came from.
field_name         "
value              One DISTINCT value.
INDEX              (entity_name, field_name, value)

Staging is wiped after every run, so a rule on entity B can't JOIN against
entity A's staged rows -- they may be gone. This table persists only the
DISTINCT values of fields an approved ref_integrity rule actually targets.
Bounded work, not a copy of the source.

--------------------------------------------------------------------------------
stg_<entity>  -- ONE STAGING TABLE PER ENTITY. Runtime only.
--------------------------------------------------------------------------------
stg_account (16 cols), stg_contact (10), stg_product (6), stg_account_team (4)

id                 Surrogate key, NOT the source Id.
run_id             Scopes the batch; makes cleanup a one-liner.
record_key         The source Id, carried through to violations.
<entity columns>   ONLY the declared CDEs -- a 443-column export is pruned to
                   these. Physical columns (not JSON/EAV) so a compiled rule
                   can say `WHERE Name IS NULL` against a real, indexable
                   column.
loaded_at          Staleness of a stuck run.

Generated at import time from the ENTITIES constant -- there is never a
runtime CREATE TABLE. Cleared after every run; never a permanent store.

################################################################################
HOW A RUN ACTUALLY EXECUTES (and why it scales)
################################################################################

  1. Create val_batches row, then one val_runs row PER ENTITY
  2. Stage the source into stg_<entity> in 5,000-row batches
     (never loads the whole file into memory)
  3. Load rules:  SELECT * FROM val_rules
                  WHERE entity_name = ? AND status = 'approved' AND active = 1
  4. For EACH rule:
       - compile rule_config_json -> SQL
       - run ONE query; the DATABASE does the work as a set operation.
         Python never loops over data rows — only over rules (dozens).
       - write violations with bulk inserts in 5,000-row chunks
       - write one val_metrics row
       - COMMIT  (one transaction per rule)
  5. Refresh val_reference_values for any field other entities depend on
     (must happen BEFORE staging is cleared)
  6. Clear stg_<entity>
  7. Mark run 'completed'  (batch status is DERIVED from its runs)

WHY IT DOESN'T BREAK AT MILLIONS OF ROWS
  - SQL pushdown: rules are set operations run by the database, not Python
    loops. A WHERE scan or GROUP BY over 5-10M indexed rows is seconds.
  - Batched writes: the real bottleneck is writing violations back. One-row-at-
    a-time inserts would take 10-20+ minutes; 5,000-row bulk chunks do not.
  - One commit per rule: if the process dies on rule 40 of 60, rules 1-39 are
    already durably committed. Partial progress survives a crash.
  - Runs execute as a BACKGROUND TASK, never inline in an HTTP request — a
    multi-minute job would otherwise blow the request timeout. The API returns
    a run_id immediately and the UI polls DQ_RUN.status.
  - Any exception marks the run 'failed' with error_message set, so a broken
    run is visible rather than silently half-done.



################################################################################
PART 3 — INSPECTING THE DATABASE (Windows + macOS)
################################################################################

The `sqlite3` command-line tool ships with macOS but NOT with Windows, which
is why the same command that works on a Mac fails on a Windows laptop. Use the
Python helper below and the commands are IDENTICAL on both.

--------------------------------------------------------------------------------
RECOMMENDED — works the same on every OS (no install needed)
--------------------------------------------------------------------------------
From the backend/ folder:

  macOS / Linux                        Windows
  ---------------------------------    ---------------------------------
  python3 inspect_db.py                python inspect_db.py
  python3 inspect_db.py val_rules      python inspect_db.py val_rules
  python3 inspect_db.py val_runs 10    python inspect_db.py val_runs 10

  # any SQL you like
  python3 inspect_db.py --sql "SELECT * FROM val_rules WHERE status='approved'"
  python  inspect_db.py --sql "SELECT * FROM val_rules WHERE status='approved'"

(Use the venv's python if the venv is not active:
   macOS:   ../venv/bin/python3 inspect_db.py
   Windows: ..\venv\Scripts\python.exe inspect_db.py )

--------------------------------------------------------------------------------
THE QUERIES YOU ACTUALLY WANT
--------------------------------------------------------------------------------
Pass any of these to --sql, or paste into the sqlite3 CLI.

-- every rule, readable
SELECT rule_id, entity_name, field_name, rule_type, severity, status,
       created_by, approved_by
FROM val_rules ORDER BY rule_id;

-- rules the engine will ACTUALLY run (the approval gate)
SELECT rule_id, entity_name, field_name, rule_type
FROM val_rules WHERE status='approved' AND active=1;

-- run history: batches and the entities inside them
SELECT b.batch_id, b.batch_name, b.run_type, r.entity_name, r.status,
       r.records_scanned, r.rules_executed
FROM val_batches b JOIN val_runs r ON r.batch_id=b.batch_id
ORDER BY b.batch_id DESC, r.run_id;

-- scores for the latest run of each entity
SELECT entity_name, field_name, dimension, severity,
       records_checked, records_failed, score_pct
FROM val_metrics
WHERE run_id IN (SELECT MAX(run_id) FROM val_runs
                 WHERE status='completed' GROUP BY entity_name)
ORDER BY score_pct;

-- the fix worklist for one run
SELECT record_key, entity_name, field_name, current_value, violation_reason
FROM val_violations WHERE run_id = 1 LIMIT 50;

-- row counts everywhere
SELECT 'val_rules' t, COUNT(*) n FROM val_rules
UNION ALL SELECT 'val_batches', COUNT(*) FROM val_batches
UNION ALL SELECT 'val_runs', COUNT(*) FROM val_runs
UNION ALL SELECT 'val_metrics', COUNT(*) FROM val_metrics
UNION ALL SELECT 'val_violations', COUNT(*) FROM val_violations;

-- staging must be EMPTY between runs (it is runtime-only by design)
SELECT COUNT(*) FROM stg_account;

--------------------------------------------------------------------------------
IF YOU PREFER THE sqlite3 CLI
--------------------------------------------------------------------------------
macOS (built in):
  cd backend
  sqlite3 smtc_dq.db
  .tables
  .headers on
  .mode column
  SELECT * FROM val_rules;
  .quit

  # one-liner
  sqlite3 -header -column smtc_dq.db "SELECT * FROM val_rules;"

Windows (sqlite3 is NOT installed by default) -- pick one:
  1. Download "sqlite-tools" from sqlite.org/download.html, unzip, and either
     add the folder to PATH or run it by full path:
         C:\sqlite\sqlite3.exe smtc_dq.db "SELECT * FROM val_rules;"
  2. Install DB Browser for SQLite (GUI) and open backend\smtc_dq.db
  3. Just use inspect_db.py above -- no install, same commands as Mac.

NOTE the path separator: macOS uses backend/smtc_dq.db, Windows uses
backend\smtc_dq.db. inspect_db.py resolves this itself, which is the other
reason to prefer it.

--------------------------------------------------------------------------------
RESETTING
--------------------------------------------------------------------------------
  python create_tables.py --reset     # drop + recreate everything (no rules)
  python seed_dummy.py --reset        # reseed the 3 demo dashboard runs
Both commands are identical on Windows and macOS.

################################################################################
CURRENT STATE / WHAT IS NOT BUILT YET
################################################################################

BUILT AND VERIFIED
  - All 8 rule types, compiled from metadata, no code per rule
  - Draft -> submit -> approve -> reject workflow (approval gates execution)
  - Chunked ingestion (CSV upload + direct DB fetch)
  - Background run execution with status polling
  - Violations captured with source Id, paginated API + streamed CSV export
  - Dashboard: overview + object drilldown, reading val_metrics only
  - Light / dark theme

NOT BUILT (deliberately, or not yet)
  - Automatic rule SUGGESTION (profiling a new column and proposing a rule).
    The no-code mechanism is done; the automation is not started.
  - Real AI integration. The "Generate with AI" button only builds a prompt to
    paste into Claude/ChatGPT/Copilot by hand — no LLM is called, because LLM
    data usage is not approved for this project.
  - Rule EDITING (rules can be created and status-changed, not edited).
  - Scheduled/nightly runs (manual trigger only so far).
  - Violations browser page (the API exists; there is no UI for it yet).
  - Rule preview/dry-run wired into the UI (the endpoint exists).
  - Real source DB connection: the 'Run from Database' UI is built and the
    query is generated per entity, but SOURCE_DB_URL must be set on the
    server. Until then those runs fail with a clear message by design.
  - Auth / users / roles — deferred by decision.
  - Remediation lifecycle on violations — deferred by decision (V1 is
    validation + violation reporting only).
  - Testing at true 5-10M scale — pending a run against the real accounts.csv.
